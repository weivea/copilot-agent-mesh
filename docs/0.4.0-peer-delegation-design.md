# Copilot Agent Mesh 0.4.0 技术设计：Peer Window Delegation

> 状态：P1–P8 已实现；真实 Copilot UI / editor 证据待运行确认<br>
> 日期：2026-08-30<br>
> 需求依据：[0.4.0 需求文档](0.4.0-peer-delegation-requirements.md)<br>
> 调研依据：[Editor Agent Host Endpoint Spike](spikes/editor-agent-host.md)<br>
> 基线：`0.3.0`，分支 `weivea-same-device-collaboration`，HEAD `3cd0646`

## 1. 设计原则

1. **不重写地基。** Device Broker、Window Node、Workspace Lease、本地认证 IPC、Task
   幂等与 generation fencing、脱敏边界全部保留，只替换编排层与 UX 层。
2. **鉴权只认稳定身份。** 一切授权判定基于 `workspaceIdentity`（`sha256:` 前缀的
   domain-separated 摘要）与 `nodeInstanceId`。显示名永远不参与判定。
3. **策略由 Broker 拥有。** 窗口是策略的编辑者，Broker 是策略的**唯一裁决者**。窗口
   不能自证「我被授权了」。
4. **默认拒绝。** 白名单默认空、接收开关默认关、Preview 开关默认关。
5. **失败必须显式。** 未授权、离线、超时、降级都返回可区分的错误码，绝不返回
   success-shaped 的空结果。

## 4. 策略存储与协议

### 4.1 存储布局

沿用既有 `mesh-state/` 根，新增：

```
mesh-state/
  peers/
    policy.json          # 单文件，原子写入（tmp + rename），带 schemaVersion
```

`policy.json` 结构：

```jsonc
{
  "schemaVersion": 1,
  "entries": {
    "sha256:<workspaceIdentityA>": {
      "windowName": "frontend",
      "windowNameFold": "frontend",        // 大小写折叠后的唯一性键
      "acceptsIncoming": false,
      "allowlist": ["sha256:<workspaceIdentityB>"],
      "updatedAt": "2026-08-30T09:00:00.000Z"
    }
  }
}
```

约束：

- `entries` 条目数上限 `256`；单个 `allowlist` 上限 `32`。
- `windowName` 复用 `PROTOCOL_LIMITS.nameBytes` 上限。
- `windowNameFold` 必须等于显示名的确定性 NFKC + `en-US` 大写后小写的 caseless
  折叠；文档内不得有重复折叠键。
- **不存储任何路径**。`workspaceIdentity` 已经是不可逆摘要，Workspace 显示名由在线节点
  在运行时提供，不落盘。
- 写入走既有的原子写入 + generation fencing 通道；非 leader Broker 不得写入。
- 唯一性读取、冲突裁决、partial policy 合并和写入位于同一个 Store 串行 mutation 中；
  不能在 Service 先查再写，否则并发同名请求会同时通过。
- P2 已写出的 schema-v1 是已知兼容格式：旧版 NFKC + 小写 fold 仍匹配的条目在启动时
  走 generation-fenced 原子改写。安全且唯一的名称保留并更新 fold；旧版允许的路径、
  Secret 形状或新 fold 冲突改为确定性的安全短 ID 回退，同时原样保留
  `acceptsIncoming`、allowlist 与 `updatedAt`。结构损坏、未知版本或连旧 fold 都不匹配的
  文档仍以 corruption 显式失败，绝不重置或丢弃策略。

### 4.2 新增协议方法

```ts
LOCAL_BROKER_METHODS = {
  // ...既有
  policyGet: 'node.policy.get',
  policySet: 'node.policy.set',
};
```

```ts
export const nodePolicyGetParamsSchema = nodeIdentityParamsSchema.extend({
  workspaceIdentity: workspaceIdentitySchema.optional(),
});

export const nodePolicySetParamsSchema = nodeIdentityParamsSchema.extend({
  workspaceIdentity: workspaceIdentitySchema,
  windowName: utf8String(PROTOCOL_LIMITS.nameBytes, 'window name', 1).optional(),
  acceptsIncoming: z.boolean().optional(),
  allowlist: z.array(workspaceIdentitySchema).max(32).optional(),
});

export const nodePolicyResultSchema = z.strictObject({
  workspaceIdentity: workspaceIdentitySchema,
  windowName: utf8String(PROTOCOL_LIMITS.nameBytes, 'window name', 1),
  acceptsIncoming: z.boolean(),
  allowlist: z.array(workspaceIdentitySchema).max(32),
});
```

`workspaceIdentitySchema` 从既有的 `z.string().regex(/^sha256:[A-Za-z0-9_-]{43}$/u)`
提取为具名 schema 复用。

### 4.3 节点目录扩展

`nodeWorkspaceSummarySchema` 增加：

```ts
workspaceIdentity: workspaceIdentitySchema,
acceptsIncoming: z.boolean(),
```

`windowNodeDescriptorSchema` 的既有 `label` 字段**复用**为窗口显示名：Broker 在返回
目录时用 `PeerPolicyStore` 中的 `windowName` **覆盖** `label`，未设置时回退到 Workspace
名，再回退到短节点 ID。这样不引入并行字段，避免两个名字打架。

唯一性覆盖当前 claimed Workspace 的**有效名称**，不只覆盖已有 Store 条目。显式存储名
优先保留；两个未命名 Workspace 的安全显示名相同时，按稳定 identity 顺序只让一个使用
该显示名，其余确定性回退到短 node ID。用户提交的重命名若撞到任一有效回退名仍返回
`WINDOW_NAME_CONFLICT`，不得静默加后缀。所有目录与 Task 来源标签复用同一次有效名分配。

### 4.4 `node.policy.set` 的裁决规则

1. 调用者必须已注册且 `nodeInstanceId` 有效。
2. `workspaceIdentity` 必须是调用者**自己已 claim** 的 Workspace，否则
   `POLICY_FORBIDDEN`。这就实现了「只能重命名自己」。
3. `windowName` 校验顺序：长度 → 字符（拒绝 `/`、`\`、`:` 组合、以 `~` 或盘符开头等
   路径形状）→ Secret 形状（长十六进制、`ghp_`/`gho_` 等前缀、具有可信字符类别与
   熵的 Base64URL 长串；普通长描述名不因长度或连字符单独拒绝）→
   大小写折叠唯一性。非法值返回 `WINDOW_NAME_INVALID`；冲突返回
   `WINDOW_NAME_CONFLICT`，**不**静默改名。
4. `allowlist` 中不得包含自身；条目必须是合法 `workspaceIdentity` 形状；不校验目标是否
   在线（离线目标允许保留）。
5. 写入成功后广播策略变更，使所有窗口的 Dashboard 与 `mesh_list_workers` 立即一致。

## 5. 双重授权门

### 5.1 求值

```
visible(source, target) :=
      target.acceptsIncoming
  AND target.workspaceIdentity ∈ policy[source.workspaceIdentity].allowlist
  AND target.node.status == 'online'
  AND target.workspaceClaim == 'claimed'
  AND target.workspaceCount == 1
```

P2 实现说明：稳定的 Language Model Tool 调用只带窗口级调用上下文，既不提供当前
Workspace 身份，也不能安全接受模型自报的来源身份。为了仍允许多根窗口作为来源且保持
默认拒绝，Broker 从已认证的精确 Window Node 派生全部当前 `claimed` Workspace，并要求
**每一个**来源 Workspace 的 allowlist 都包含目标。后续若稳定 API 提供可认证的单一
Workspace 调用上下文，可收敛为只求值该身份；不得用未认证请求字段替代。

原始 `node.policy.get` 只有窗口身份，在多根来源窗口中无法读取每个 Workspace 的独立
策略，也就无法安全完成上述全量 allowlist 的 read-modify-write。P2 因此允许调用者附带
`workspaceIdentity`，但 Broker 必须把它与已认证窗口当前 `claimed` 的身份集合匹配；
外部身份返回 `POLICY_FORBIDDEN`。省略字段只保留给恰好一个已 claim Workspace 的便利
路径。该字段只选择调用者自己的策略，不参与任务来源认证。

### 5.2 执行点

| 执行点 | 行为 |
| --- | --- |
| `node.list`（服务 `mesh_list_workers`） | 过滤掉不可见节点；不泄漏其存在 |
| `node.task.start` | 再次求值。不可见时按原因返回可区分错误码 |
| Dashboard 节点列表 | **不**过滤：用户需要看到全部本设备节点才能勾选，但显示每项的门状态 |

> 注意 `node.list` 与 Dashboard 的差异是刻意的：Tool 面必须遵守最小可见性，配置面必须
> 能看到候选项。两者走不同的 Broker 方法，Dashboard 用的那条**只**返回显示名、
> Workspace 名、在线状态与门状态，不返回任何路径。

### 5.3 错误码

| 码 | 触发 |
| --- | --- |
| `PEER_NOT_ALLOWED` | 来源未勾选目标 |
| `PEER_NOT_ACCEPTING` | 目标接收开关关闭 |
| `PEER_OFFLINE` | 目标节点不在线 |
| `PEER_MULTI_WORKSPACE` | 目标 claim 了多于一个 Workspace |
| `WINDOW_NAME_CONFLICT` | 重命名冲突 |
| `WINDOW_NAME_INVALID` | 名称越界，或包含路径、控制/不可见字符、Secret/Token 形状 |
| `POLICY_FORBIDDEN` | 试图修改非自身 Workspace 的策略 |
| `DELEGATION_RECURSION` | 子任务上下文发起委派 |

`PEER_NOT_ALLOWED` 与 `PEER_NOT_ACCEPTING` 必须可区分，因为二者的用户修复动作不同
（一个在来源窗口勾选，一个在目标窗口开开关）。

## 6. 委派：长时 Tool 调用

### 6.1 `mesh_delegate_task` 生命周期

```mermaid
sequenceDiagram
  participant U as 用户（窗口 A）
  participant C as Copilot
  participant T as mesh_delegate_task
  participant B as Broker
  participant N as 窗口 B Node
  participant H as Agent Host

  C->>T: prepareInvocation(input)
  T-->>U: 确认（Continue / Cancel）
  U-->>T: Continue
  C->>T: invoke(options, token)
  T->>B: node.task.start（含 idempotencyKey + grant）
  B->>B: 双重授权门 + Workspace Lease
  B->>N: node.task.start
  N->>H: createSession + 首轮 dispatch
  H-->>N: agentStarted / output / turnComplete
  N-->>B: node.task.event
  B-->>T: 权威终态或 needsInput
  T-->>C: 结构化结果（始终含 taskId）
```

### 6.2 等待器（`DelegationWaiter`）

```ts
type DelegationOutcome =
  | { kind: 'completed'; taskId: string; result: BoundedResult }
  | { kind: 'needsInput'; taskId: string; inputId: string; question: string }
  | { kind: 'failed'; taskId: string; code: string; message: string }
  | { kind: 'cancelled'; taskId: string; reason: 'token' | 'budget' | 'peer' };
```

规则：

1. 等待条件为**权威**状态变更事件，不是轮询快照。
2. 预算来自既有输入字段 `timeoutMinutes`：**默认 60**，上限由 0.3.0 的 `1440` **收紧到
   `60`**——调用现在会阻塞整轮对话，1440 分钟的上限不再合理。由单个 timer 驱动，
   **必须**在所有出口路径 dispose。
3. 预算耗尽 → 发 `node.task.cancel` → **继续等待**权威 `cancelled`/`failed` → 返回
   `{ kind: 'cancelled', reason: 'budget' }`。**不允许**在未确认终态前返回。
4. `token.onCancellationRequested` 走同一条精确取消路径，`reason: 'token'`。
5. `needsInput` 是**正常返回**，不是失败：把问题交回父 Copilot，让它在 A 的对话里问
   用户，再用 `mesh_answer_task` 投递到精确 `inputId`。
6. 无论哪条出口，返回体**始终**包含 `taskId`。这是「调用被宿主中断也不丢任务」的唯一
   保障。

### 6.3 结果契约变更

0.3.0 的紧凑结果是「已受理 + pending」语义（`s` 0=accepted pending、1=reconcile、
2=error、3=persistence pending，配合 `t`/`d`/`e`/`r`）。0.4.0 改为终态语义，需要重新
定义并同步 `modelDescription`：

| 字段 | 含义 |
| --- | --- |
| `s` | `0` completed、`1` needsInput、`2` failed、`3` cancelled |
| `t` | `taskId`（**所有**分支都必须存在） |
| `d` | `delegationRequestId` |
| `e` | 稳定错误码（`s=2`/`s=3` 时） |
| `i` | `inputId`（仅 `s=1`） |
| `q` | 有界问题文本（仅 `s=1`） |
| `r` | 有界结构化结果摘要（仅 `s=0`） |
| `x` | 取消原因 `token` / `budget` / `peer`（仅 `s=3`） |

`modelDescription` 必须明确写出：**不再需要用 `mesh_get_task` 轮询正常路径**；
`mesh_get_task` 的定位收敛为「调用异常中断后的追查」与「查询他人发起的任务」。

### 6.4 幂等

`mesh_delegate_task` 输入携带 `delegationRequestId`（沿用 0.1 Spike 已验证的语义）。
Broker 以 `(callerWorkspaceScopeIdentity, delegationRequestId)` 为幂等键。单根来源窗口的
scope identity 就是该 Workspace identity；多根来源窗口则使用全部当前 `claimed`
Workspace identity 排序后的 canonical set hash。该 scope 不依赖 active editor，因而同一请求
在编辑器焦点改变或没有 active editor 时仍恢复同一任务。来源窗口的 claim 集合实质变化时
会得到不同 scope；P2 的方向授权仍针对认证来源 Node 的完整 claim 集合逐项检查，不使用
scope hash 替代授权。现有协议字段 `sourceWorkspaceIdentity` 在 0.4.0 保留 wire 名称以避免
协议漂移，但其 P4 幂等语义是这里定义的 source Workspace scope identity。

- 首次 → 创建任务，记录 `taskId`；
- 重试（同键、同语义）→ **复用**原 `taskId`，不重复启动；
- 同键但语义不同 → `IDEMPOTENCY_CONFLICT`。

Broker 接管（generation 变更）后，幂等表随任务状态一起从持久化恢复，因此接管不会导致
重复执行。

### 6.5 确认 UI

依据 Spike 第 7 节，`PreparedToolInvocation.confirmationMessages` 只有 Continue /
Cancel。因此：

```
title:   Delegate to “backend”
message: 目标窗口：backend
```

## 7. 授权范围（DelegationGrant）

```ts
interface DelegationGrant {
  readonly taskId: string;
  readonly workspaceIdentity: string;   // 仅此 Workspace
  readonly autoApprove: readonly ['localTerminal', 'localFileWrite'];
  readonly neverAutoApprove: readonly ['networkAuth', 'crossWorkspaceWrite', 'secretAccess', 'externalPublish'];
}
```

`grant` 随 `node.task.start` 下发，由目标窗口的 `WindowNodeTaskExecutor` 执行。映射到
既有的 `AgentInputKind`：

| `AgentInputKind` | 处理 |
| --- | --- |
| `toolConfirmation` | 若操作落在 `grant.workspaceIdentity` 内且属于 `autoApprove` 类别 → 自动批准；否则升级 `needsInput` |
| `toolAuthentication` | **一律**升级 `needsInput` |
| `chatInput` | **一律**升级 `needsInput` |

`grant` 的生命周期严格等于任务生命周期，随任务终态一起销毁。**不写盘、不按节点对缓存、
不跨任务复用**。既有的 `FirstTaskConfirmation`（`'once' | 'always' | 'deny'`）在 0.4.0
中收敛为 `'once' | 'deny'`：`'always'` 语义与「仅限本次任务」冲突，予以移除。

判定必须**默认拒绝**：无法确定某次 `toolConfirmation` 的目标路径是否在
`grant.workspaceIdentity` 内时，升级为 `needsInput`，而不是放行。

固定 AHP `f19dd8b3942d029744a3bdd31d830f9428e8ea47` 的
`ChatToolCallReadyAction` 只为文件修改提供权威结构化范围：
`edits.items[].before/after.uri`。`toolInput` 可以是任意字符串或 `ContentRef`，
`_meta.ptyTerminal` 和工作目录也不能证明任意 shell 命令不会认证网络、读取密钥、发布内容
或重定向写出 Workspace。因此 P5 只自动批准已知 `write_file` 调用中每个 URI 均经
canonical/realpath 检查留在精确 Workspace 内的结构化文件修改；新文件还要求其直接父目录
已存在并可 canonicalize，目标目录项经两次 `lstat` 均确认不存在，且其父目录在确认前后
解析为同一 canonical 路径；dangling symlink、junction/reparse 不确定性或确认期间可见的
替换一律升级。检查同时覆盖 Workspace root 的完整 canonical ancestry，防止把
`.git/hooks` 等 control-plane 子目录本身注册为 Workspace 来绕过相对路径策略。版本控制
hook/config、包管理器 manifest/lock/auth 配置、编辑器 task/workspace/启动配置、CI
workflow/action、自动加载的 Agent instruction/prompt 与 devcontainer 等可触发命令、
认证、持久指令注入或发布的 Workspace control-plane 路径也不自动批准。
`localTerminal` 仍保留在
grant 的协议能力声明中，但本版没有足够证据将任何终端确认归入该类，全部升级为
`needsInput`。结果确认、未知工具、缺失/相对/编码/UNC/drive 路径、symlink 逃逸以及任一
路径越界的多路径操作也全部升级。

Client initialize 的 offer 被明确收紧为且仅为 `["1.0.0"]`，editor 与 standalone 使用
相同约束；服务端若返回未 offer 的 legacy 版本，会在任何 Session/Turn effect 前失败。

## 8. Agent Host 来源选择

### 8.1 选择顺序

```
1. EditorAgentHostLocator.locate()
   → code agent endpoints --user-data-dir <推导目录>
   → 筛选 type === 'editor' 且 protocolVersion 满足 ^1.0.0
   → 命中：UnixSocketWebSocketConnector 连接，source = 'editor'
2. 失败 → AgentHostLauncher（0.3.0 现状），source = 'standalone'（降级）
```

`source` 必须上报到 Dashboard 与 E2E 证据。降级时 UI 显式标注
`Standalone (degraded)`，并说明子任务不会出现在 Chat Sessions 列表中。

P6 的 `AgentHostSourceSelector` 只在默认关闭的
`experimental.peerDelegation` 打开时优先选择 editor；开关关闭时继续使用既有
standalone 路径且不标记降级。每次任务为 editor endpoint 建立独立 AHP/WebSocket
Client，连接处置互不影响。发现、连接或 AHP `initialize`/协议失败时只尝试一次
standalone，并通过有界枚举状态通知组合层；认证、配置、标题或已开始 Turn 的失败不会
重跑任务。

P6 follow-up 把确认边界提升到 source selector 之外：一个 WeakMap-backed、仅 Extension
Host 内存可识别的 capability 绑定完整 runtime request，并同时覆盖 editor 与最多一次
standalone attempt。Broker grant 经 `assertDelegationGrantBinding` 精确验证后，只有带
本地 `sourceNodeId` 的 same-device peer task 才由执行器签发该 capability，目标窗口不再
显示 Node/runtime modal；父窗口 `prepareInvocation` 的 Continue/Cancel 是唯一 consent。
没有本地来源证明的 legacy/cross-device/direct task 仍在目标只确认一次，确认后才签发同一
capability 给 runtime。wire boolean、grant 文档或模型字段都不能构造/伪造该对象。

### 8.2 user-data 目录推导

不得硬编码。按平台与运行形态推导，并允许配置覆盖：

| 平台 / 形态 | 目录 |
| --- | --- |
| macOS 稳定版 | `~/Library/Application Support/Code` |
| macOS Insiders | `~/Library/Application Support/Code - Insiders` |
| Linux | `$XDG_CONFIG_HOME/Code` 或 `~/.config/Code` |
| Windows | `%APPDATA%\Code` |
| 便携模式 / 自定义 | 由新增配置 `copilotAgentMesh.agentHost.userDataDir` 覆盖 |

推导失败或 `code agent endpoints` 的 `userDataPath` 与预期不符时**直接回退**到
standalone，不做猜测重试。

### 8.3 传输

```ts
// 概念代码
const socket = net.connect(endpoint.endpoint.path);
const ws = await upgradeToWebSocket(socket, `/?tkn=${endpoint.connectionToken}`);
const transport = WebSocketTransport.fromSocket(ws);
const client = new AhpClient(transport, { requestTimeoutMs: 30_000 });
```

Extension Host 的全局 `WebSocket` 不能拨号 Unix socket（见 Spike 第 3 节），因此握手在
Node 侧完成后再交给既有 transport。`ws@8.21.3` 已是仓库依赖，无需新增。

P6 实现先用 `net.connect({ path })` 建立 Unix socket，再让 `ws@8.21.3` 仅通过该已建立
socket 发起标准 `GET /?tkn=...` Upgrade；禁用重定向、扩展和压缩，并严格验证 101、
`Upgrade`、`Connection` 与 `Sec-WebSocket-Accept`。握手完成后清除 `ws.url` 中的查询，
所有失败只返回稳定枚举消息，不携带底层 `cause`。

### 8.4 敏感值处理

`connectionToken`、socket 路径、user-data 路径进入既有 `sanitizeError` 的 redaction 集合。
新增测试断言：这三类值不出现在任何 Webview 消息、任务输出、日志或错误消息中。

P6 同时把 CLI executable 与 endpoint instance ID 注册到引用计数、只存内存的动态脱敏
集合；并覆盖原文、percent-encoded、JSON/cause/AggregateError 文本。最后一个使用该
endpoint 的任务处置后删除注册，多个并发任务不会提前删除共享值。

### 8.5 Session 标题

`createSession` 无 `title` 字段（Spike 第 5 节），标题需在会话建立后通过
`session/titleChanged` action 设置：

```
Mesh · <来源窗口名> → <任务摘要，有界>
```

标题必须经过与 Webview 相同的脱敏校验：不含路径、不含 Secret、长度有界。任务终止时
必须明确处置该 Session（不留「运行中」假象）。

P6 在 `createSession` 并订阅精确 Session channel 后派发标题 action，并等待带本客户端
origin 的服务端 acknowledgement；拒绝或超时会删除尚未运行的 Session。editor Turn
达到权威 `turnComplete`/`turnCancelled`/`chat/error` 后只关闭订阅、AHP Client 与
WebSocket，不调用会广播 `root/sessionRemoved` 的 `disposeSession`，从而保留用户可见
历史；standalone 仍按原生命周期 dispose Session 与 owned Host。固定 AHP Host 在连接
断开时会移除 active client，且子 Session 的 `activeClient.tools` 为空。

## 9. 递归防护

1. 注入 Mesh Tools 的唯一路径是窗口的正常 Extension Host 激活。
2. `WindowNodeTaskExecutor` 创建子任务 Session 时，`activeClient.tools` 保持为空数组
   （0.3.0 已如此），且**不**注册任何 Mesh Tool provider。
3. Broker 为每个已接受任务生成 256-bit 随机 capability，绑定精确 task、目标 Node
   instance 和当前认证 IPC session，只随内部 `node.task.start` 交给可信执行器并仅在活跃
   任务内存中持有。携带该 live capability 的后续 start 返回 `DELEGATION_RECURSION`；
   capability 伪造、跨 Node/session 使用或任务终态后复用返回认证失败。
4. 所有本地 start 都必须携带 Broker 签发的 principal，省略或伪造会在路由前失败。窗口
   用户自己的 Chat 使用 `node.register` 返回且绑定当前 Node/session 的 window principal；
   执行器只能使用精确任务的 child principal。因而即使同一窗口正在为 A 执行子任务，它仍
   可作为自己对话的主节点向 C 委派，而 child principal 不能降级成匿名/window 调用。
5. 生产 Extension Host 维护一个有界、短时、只存内存的调用关联表。可信 AHP task 在其精确
   Chat 收到 `chat/toolCallStart` + `chat/toolCallReady` 时，仅对
   `mesh_delegate_task` 的最终 inline `toolInput` 计算 canonical SHA-256 指纹，并把指纹与该
   task 的 Broker child principal、AHP Session/turn/tool-call identity 关联；不保存或记录原始
   prompt。真实 `MeshDelegateTaskTool` 消费唯一匹配项，并让 `TaskToolsCore` /
   `LocalBrokerTaskFacade` 选择既有 `startTaskFromDelegatedChild` 或 remote 对应路径，使
   Broker 在真实工具调用链返回 `DELEGATION_RECURSION`。
6. 每个观测项首次消费后保留为 claimed tombstone，直到权威 `toolCallComplete` 或更强生命周期
   清理；重复调用继续取得同一 child principal，不得降级为 window principal。相同指纹的并发
   观测按有界队列逐项 claim，容量回收与观测 TTL 不得逐出已 claim 项；claimed tombstone
   仅由权威生命周期清理。总数量、单 Session 数量与未 claim 观测 TTL 均有上限；伪造、过期、
   `ContentRef`、未知工具或
   非法输入不产生 child principal。tool complete、任务终态/取消/处置、AHP reconnect 以及
   Extension Host/Broker takeover 都清理关联。VS Code 的 `toolInvocationToken` 是 opaque，
   稳定 API 无法安全读取，因此不作为身份依据；reconnect replay/snapshot 阶段禁用观测，恢复
   完成后仅接受新的实时 tool-call action，避免恢复旧 capability。
   稳定 Tool API 也不提供可与 AHP Session 直接核对的调用身份，因此只有仍存活的正向匹配可证明
   child principal；缺失、未 claim 过期或因容量上限未保留的观测必须保持普通 window 调用语义，
   否则任意伪造关联即可阻断同窗口的用户 Chat。该限制使空 child Tool 集仍是主要安全边界，
   production correlation 只为实际观测且及时匹配的异常 child 调用提供 Broker defense-in-depth。
7. 单元、Extension Host 与组件测试断言：子任务运行期间，目标窗口执行器可见的工具集合中不含任何
   `MESH_TOOL_NAMES` 成员。

### 10.4 P7 安全操作句柄与任务分区

P7 的配置目录继续与 Tool 目录分离。`node.policy.candidates` 返回全部本机候选（包括
未授权、未接收、多 Workspace、自身状态和已持久化的离线 allowlist 条目），但每个可变项
只携带 Broker 为当前认证 IPC Session 签发的一次性随机句柄。句柄绑定精确来源
Workspace identity、目标 Workspace identity 和在线时的精确 Node instance；刷新、策略
变化、消费、断线或处置后失效。在线目标在 mutation 时重新核对 instance/claim，离线条目
只允许撤销。Webview 再为每个 `uiInstanceId` 包一层一次性句柄，所以跨 View、重放、错误
方向或旧 Snapshot 都不能修改策略。

Dashboard Task 目录由 Broker 按认证 Window Node 分区：`Outgoing` 只含
`sourceNodeId` 为本窗口的任务，`Incoming` 只含精确目标 Node instance 的任务。返回值仅有
安全来源/目标名、Workspace 显示名、有界标题、状态、开始时间和 8 位显示 ID。取消句柄在
Broker 内绑定精确 task ID 与方向；Outgoing 走来源 owner 路径，Incoming 走目标 Node
授权路径。打开确认框前，显示句柄先兑换成独立、有界的 in-flight reservation；普通刷新
不会使已展示的确认失效，确认取消时显式释放，执行时一次性消费。终态 cancel 保持幂等，
但终态不签发新的 Dashboard 取消句柄。Remote outgoing 状态由权威 task snapshot
notification 更新到有界的每窗口 cache，合并列表排序后严格截断到 500 项并显示告警。

P7 follow-up 使 active Task 的 Broker 句柄按精确 owner/task/direction 复用，Webview 别名按
`uiInstanceId` 与同一 Broker 句柄复用；output/progress/tool 等不改变 Dashboard 字段的事件
既不轮换句柄也不触发 Dashboard 刷新。状态变化按每 Session/event-loop 合并，终态、Node/
route/ownership generation 变化立即使未 reserve 的句柄失效，reserve 在 commit 时再次核对。
Broker 在 takeover 初始化时一次扫描 Task Store，之后由 durable transition 更新一个
generation-scoped、1000 项上限的内存索引；每项是严格 schema 验证、冻结且不超过 1 KiB 的
最小投影，只保留 task/owner/source/target/workspace/state/title/timestamps，不保留 event
journal、output、input、failure payload、recovery、answer 或 runtime/grant 数据。Dashboard
read 只复制该小投影，不再进入 FileTaskStore 全量扫描。Reserve/commit 的取消授权仍通过精确
Task Store record 与 live route 重新验证，不把索引当作授权权威。
所有 protocol-valid offset/任意允许小数精度时间在 Presenter 中转成标准三位毫秒 `Z` 时间；
无法安全转成四位年份 canonical ISO 的值只显示 `Unknown`，不会使整个 ViewModel 失败。
